# Hindsight: модели, роли и где реально теряется время

Дата снятия: 2026-10-30. Источник — `llm_requests` в базе Hindsight (`pg0`, Postgres 18.1), окно 7 дней. Все числа ниже — наблюдённые, не оценочные.

## Инвентарь ролей

Одна «модель Hindsight» — неверная формулировка. Ролей пять, и они разные.

| Роль | Значение | Провайдер |
|---|---|---|
| Извлечение фактов (`retain`) | `upstage/solar-mini4:free` | openai через `hermes-proxy:8645` (nous) |
| Синтез (`reflect`) | `mistral-small-3.2-24b-instruct` | bothub (`openai.bothub.chat`) |
| Консолидация | `reflection/beam-1.0-501b-a23b:free` | — |
| Консолидация, failover | `gpt-6-luna` | chatgpt |
| Реранкер | `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` | **локально, CPU** |
| Эмбеддер | `sentence-transformers/paraphrase-*` | локально |

Конфигурация — переменные окружения контейнера, не банка. В конфиге банка `hermes` лежит только `retain_mission`.

## Где теряется время

**Реранкер, а не LLM.** Это главный вывод, и он измерен, а не выведен из общих соображений.

Реранкер получает `input_count` кандидатов на каждый recall. Распределение за 7 дней:

| Кандидатов | Вызовов | Среднее | Максимум |
|---|---|---|---|
| **300** | 164 | **28 465 мс** | **146 280 мс** |
| 80 | 15 | **8 880 мс** | 25 228 мс |
| 235 | 1 | 6 933 мс | 6 933 мс |

Одна и та же модель, одно железо, разница **в 3,2 раза**. То есть `candidate limit` — прямая ручка задержки, и её изменение видно сразу.

Побочный факт: 164 из 180 вызовов идут с 300 кандидатами, то есть это не случайный хвост, а штатный режим.

## Почему `reflect` падает по таймауту

`reflect` — не один вызов. За час 2026-10-30 15:00 в базе 10 записей на 341 секунду суммарно. Один `reflect` — это несколько последовательных шагов: эмбеддинг запроса, несколько проходов реранкера по 60–80 секунд, затем LLM на 50–163 секунды. При таймауте 300 секунд (`HINDSIGHT_API_REFLECT_LLM_TIMEOUT=300`) этого не хватает.

То есть `504` — арифметика, а не сбой: сумма шагов превышает бюджет.

## Ошибки

Три `CancelledError` на реранкере: 66 560 мс, 116 426 мс, 146 280 мс. Все — `recall`. Клиент отменял запрос, не дождавшись реранка. Это не отказ модели, а следствие задержки выше.

## Что из этого следует для #33

Гипотезы проверяются по отдельности, каждая — замером:

1. **Ограничить кандидатов.** Самое дешёвое: 300 → 50–80 даёт ~3x по задержке. Вопрос — потеря в качестве, её надо мерить на golden-сете (17 вопросов с hard negatives), а не на глаз.
2. **Сменить модель реранкера.** L6 вместо L12: по прошлым замерам на VPS было ~6,2 с. Требует сравнения top-1/top-3 на том же golden-сете, потому что L6 слабее на мультиязычных парах.
3. **Кэш.** Эмбеддинг запроса уже быстрый (196 мс); кэшировать имеет смысл повторные recall по близким запросам.
4. **Бюджет `reflect`.** Либо сократить число шагов, либо поднять таймаут, либо признать инструмент непригодным для синтеза и не обещать его.

Модель извлечения (`solar-mini4`, 25 с) — **не первый подозреваемый**. Даже если она ускорится вдвое, recall останется медленным, потому что его тормозит реранкер.

## Как снимать эти данные снова

```
docker cp q.sh hindsight-api:/tmp/q.sh
docker exec hindsight-api /tmp/q.sh -c "SELECT operation, model, count(*), round(avg(duration_ms)) FROM llm_requests GROUP BY 1,2;"
```

`q.sh` — обёртка, которая берёт пароль из `instance.json` внутри контейнера; пароль не попадает в командную строку и в историю.

## Границы

- Окно 7 дней; поведение на длинных батчах не измерялось.
- `input_count` известен только для вызовов, где API его пишет (`llm_info`). Для остальных строк поле пустое.
- Железо: тот же ноутбук, что и остальная работа. Замеры на нём не переносятся на VPS без повторного прогона.
