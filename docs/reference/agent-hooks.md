# Хуки плагинов Hermes: что реально умеет `pre_tool_call`

Дополнение к upstream-документации (`hermes-agent/references/agent-hook-plugins.md`),
которая описывает только `action: "block"`. Здесь — то, что проверено чтением кода
Hermes v0.22.5, с указанием мест, где это лежит. Upstream не копируется: копия
стареет молча, оригинал читается в профиле.

## Три действия, а не одно

`pre_tool_call` может вернуть директиву. В коде разбираются **три**:

| `action` | Что делает | Поля |
|---|---|---|
| `block` | запрещает вызов, сообщение становится результатом инструмента | `message` |
| `approve` | эскалирует вызов на подтверждение человеком | `message`, `rule_key` (гранулярность `[a]lways`) |
| `modify` | подменяет аргументы до вызова | `args` (частичный dict) |

Источник: `hermes_cli/plugins.py`, датакласс `_PreToolCallDirective` и функция
`_get_pre_tool_call_directive_details`; применение — `agent/tool_executor.py:683` и
`agent/agent_runtime_helpers.py:2501`.

## Приоритет

`block` > `approve` > нет директивы, **независимо от порядка регистрации плагинов**.
Любой валидный veto побеждает ранее зарегистрированный запрос на подтверждение;
среди `approve` выигрывает первый валидный.

## `modify`: как именно

```python
if action == "modify":
    partial = result.get("args")          # частичный словарь
    if isinstance(partial, dict) and partial:
        modified_args = {**накопленное, **partial}
```

Три следствия, каждое важно:

1. **Shallow merge, не замена.** Передавать надо только изменяемые ключи; остальные
   аргументы сохраняются. `{"args": {"char_limit": 30000}}` не сотрёт `urls`.
2. **Накопление между плагинами.** Каждый `modify` мержится в общий словарь,
   построенный из исходных аргументов. Два плагина могут править разные ключи.
3. **`modify` обрабатывается раньше гейта** `block`/`approve`. Модификация видна,
   даже если другой плагин затем блокирует вызов — то есть порядок «кто прав» не
   зависит от того, кто вернул директиву первым.

Пустой или не-словарный `args` игнорируется: `modify` без полезной нагрузки — no-op,
а не ошибка.

## Почему это важнее, чем кажется

Правило в скилле — совет: оно работает, пока агент его помнит. Хук — механизм:
он срабатывает независимо от того, вспомнил ли агент.

Пример из практики (2026-09): агент девять раз из десяти передавал `char_limit`
вдвое-втрое ниже дефолта и терял 97% документации. Запись в скилл это не
останавливает — она объясняет. `modify` останавливает: аргумент правится до вызова,
независимо от намерения агента.

## Когда блокировать, а когда советовать — три случая с адресами

Механизм сильнее совета, но ошибка механизма дороже ошибки, которую он ловит.
Три наших случая, каждый с местом, где это проверяется.

### 1. Блокирующий гейт дважды заблокировал сам себя

`issue-guard` (создан 2026-10-29) требовал записать вывод в задачу до перехода к
другой работе. Отключён 2026-10-30 и с тех пор лежит в `config.yaml:322-324`
(`plugins.disabled`).

Проверять здесь — `state.db`, сессия `local-a347ac1f15b5407f3b…`, 2026-10-30:

```text
22:35  «issue-guard заблокировал даже `gh issue create`. Он требует комментарий
        в существующую задачу, но не даёт создать новую — замкнутый круг.»
22:37  «Гейт блокирует даже собственную диагностику: `hermes plugins doctor
        issue-guard` не дошла до исполнения. Из этого сеанса исправление тоже
        заблокировано.»
22:45  «старый issue-guard специально не пропускал `gh issue create` — признавал
        записью только комментарий к уже существующей задаче»
```

Два разных дедлока. Первый: запись результата возможна только комментарием в
существующую задачу, а новая задача не создаётся. Второй, тяжелее: гейт
блокировал `hermes plugins doctor` — то есть единственный способ себя починить
изнутри. Оба раза выход был один: правка `config.yaml` снаружи, человеком.

### 2. Напоминание: мусор вместо остановки

Механизм nudge предлагал сохранить что-нибудь в память или написать скилл.
Отключён: `config.yaml:163` (`memory.nudge_interval: 0`), `config.yaml:237`
(`skills.creation_nudge_interval: 0`).

След: `%LOCALAPPDATA%/hermes/backups/pending-memory-20261101/` — **60 файлов**
предложений за 2026-10-03…2026-10-30, ни одно не было прочитано.

Цена ошибки: мусор в каталоге, убирается одной командой. Работа не вставала.

### 3. Фоновые правки: не туда, но не блокирующе

`background_review` (`config.yaml:107`, `enabled: false`) правил скиллы и память по
своей карте адресатов, которая знает два файла из пяти. Правки 2026-10-30 17:54,
описаны в #143:

```text
observability                 копия профиля, источник в .agents/skills/
                              принята в репозиторий: PR #140
matt-pocock/research          КОПИЯ UPSTREAM — при синхронизации перезапишется,
                              правка потеряется
test-driven-development       только в профиле, вне git
```

Цена ошибки: три скилла поправлены, две правки из трёх жили в копиях и были бы
потеряны при синхронизации. Работа не вставала, откат не потребовался.

### Правило

Блокировать (`block`) можно только при трёх условиях одновременно:

1. признак машинно надёжен — ложных срабатываний нет или они дешевле пропуска;
2. есть гарантированный выход из блокировки, известный до того, как она сработает;
3. у гейта есть путь починить самого себя изнутри — он не блокирует свою
   диагностику и своё обновление.

Если хотя бы одного нет — `approve` вместо `block`. Там, где ошибку можно
исправить молча, — `modify`.

История это подтверждает асимметрией: два механизма из трёх стоили мусора,
третий остановил работу. Остановил именно тот, который должен был предотвращать
ошибки.

## Что проверить перед тем, как на это опираться

- `pre_command` в v1 — **observer-only**: директивы игнорируются, rewrite обещан
  отдельной middleware-веткой (`#64204/#64231`). Не путать с `pre_tool_call`.
- Хук видит аргументы **после** нормализации, но **до** валидации инструментом: если
  подменить значение на недопустимое, ошибку вернёт сам инструмент.
- `rule_key` в `approve` определяет гранулярность «больше не спрашивать». Один и тот
  же ключ для разных инструментов склеит их в одно разрешение — давать разные.

## Как перепроверить выводы этого раздела

Каждое утверждение выше проверяется без доступа к нашему разговору:

| Утверждение | Где смотреть |
|---|---|
| issue-guard отключён | `$LOCALAPPDATA/hermes/config.yaml:322-324` |
| два дедлока 30.10 | `state.db`, `messages`, `session_id like 'local-a347ac1f%'`, `timestamp` 2026-10-30 22:35–22:45 |
| nudge выключен | `config.yaml:163` (memory), `config.yaml:237` (skills) |
| 60 файлов предложений | `$LOCALAPPDATA/hermes/backups/pending-memory-20261101/` — `ls *.json \| wc -l`, mtime 2026-10-03…10-30 |
| background_review выключен | `config.yaml:107` |
| три правки 17:54 и их судьба | issue #143, таблица правок |
| плагин создан 29.10 | mtime файлов в `plugins/issue-guard/` |

Запрос дедлоков целиком:

```bash
python -c "import sqlite3,datetime,os; c=sqlite3.connect('file:'+os.path.expandvars(r'%LOCALAPPDATA%\hermes\state.db')+'?mode=ro',uri=True); [print(datetime.datetime.fromtimestamp(t).strftime('%H:%M'), b[:90]) for t,b in c.execute(\"select timestamp,content from messages where session_id like 'local-a347ac1f%' and content like '%issue-guard%' and length(content)<700 order by timestamp\")]"
```

Снимок, на котором это проверялось: 2026-11-02, 06:4x. Номера строк в `config.yaml` могут уехать после правок конфига — при перепроверке искать по ключу (`plugins.disabled`, `nudge_interval`, `background_review.enabled`), а не по номеру.
