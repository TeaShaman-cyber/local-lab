# Disaster recovery: что делать, если данных нет

План на случай, когда обычные механизмы не спасают: база повреждена, диск умер,
ноутбук потерян, репозиторий бэкапа сломан. Инструкция по восстановлению одной
базы — `state-db-restore.md`; здесь — контур целиком и порядок действий.

## Что защищаем

| Данные | Где живёт | Копия 1 | Копия 2 | RPO |
|---|---|---|---|---|
| `state.db` (сессии, поиск) | `%LOCALAPPDATA%\hermes\state.db` | снапшоты `E:\theseus-backups\state-db\snapshots` (6 ч, 7 шт) | restic local → S3 → drive (03:00) | 6 ч |
| Hindsight (`hindsight.dump`) | Docker volume | staging → restic | то же | 24 ч |
| Codex history | `~/.codex` | staging → restic | то же | 24 ч |
| Конфиги Hermes (`config.yaml`, cron, hindsight) | `%LOCALAPPDATA%\hermes` | staging → restic | то же | 24 ч |
| Репозитории (`E:\local-lab` и др.) | диск | GitHub (`TeaShaman-cyber/*`) | — | по коммитам |
| Секреты | `.env`, `.s3-env`, `.restic-password` | **только диск** | — | **нет** |

`staging` (`D:\theseus-backups\staging`, 2,1 ГБ) — не копия, а сборочная площадка:
`prepare_snapshot.py` делает консистентные дампы, `run_backup.py` отправляет их в
три репозитория и проверяет восстановлением.

## Топология

```
state.db ──6ч──> snapshots (E:)          ← быстрое восстановление, тот же диск E
       └──03:00──> staging (D:) ──> restic local (D:)
                                     restic s3 (twcstorage)
                                     restic drive (rclone)
```

Три репозитория — не избыточность ради галочки: `local` лежит на том же ноутбуке и
защищает только от порчи данных, а не от потери машины. От потери машины защищают
`S3` и `drive`.

## Сценарии

### A. База повреждена, машина жива

Действовать по `state-db-restore.md`. Источник — снапшот с `E:`, восстановление
минуты. Если снапшотов нет — из restic local.

### B. Диск `E:` умер

Снапшоты пропали, но `D:` и restic целы:

```bash
restic -r D:/theseus-backups/restic --password-file D:/theseus-backups/.restic-password \
  restore latest --target C:/restore --include "*hermes-state.db"
```

Затем поставить файл на место по шагам 3–6 из `state-db-restore.md`.

### C. Диск `D:` умер (restic local и ключи)

Ключи пропали вместе с диском — **см. раздел «Дыра»**. Если ключ восстановлен из
внешней копии:

```bash
restic -r s3:https://s3.twcstorage.ru/theseus-lab-backups/restic snapshots --latest 3
```

### D. Ноутбук потерян или украден

1. Сменить пароли: GitHub, S3, Hermes, Nous.
2. Отозвать токены GitHub, которыми пользовались агенты.
3. На новой машине: поставить Hermes, Python 3.13, rclone, restic.
4. Достать restic-пароль из внешней копии (password manager).
5. `restic restore latest` из S3 или drive.
6. Развернуть `E:\local-lab` из GitHub.
7. Восстановить `state.db` по `state-db-restore.md`.

**Ключевой риск**: пункт 4. Без пароля остальные шаги бесполезны, потому что
репозиторий зашифрован.

### E. Репозиторий restic повреждён

`restic check` показывает ошибки → восстанавливаться из **другого** репозитория
(S3 ↔ drive ↔ local). Именно поэтому их три. Повреждённый репозиторий не
ремонтировать на живой системе: сначала снять копию, потом разбираться.

### F. Пароль restic утерян безвозвратно

`UNKNOWN`. Репозиторий зашифрован, восстановления нет. Единственный оставшийся
источник — снапшоты `state.db` на `E:` (не зашифрованы) и GitHub для кода.

## Дыра, которую нужно закрыть

`.restic-password` (43 байта) и `.s3-env` (203 байта) существуют **только** в
`D:\theseus-backups`. Проверено 31.10.2026: копий вне `D:` нет.

Это значит: сценарий D (потеря ноутбука) сейчас **не выполним** — бэкап в S3 есть,
но расшифровать его нечем.

Что сделать (вне машины, руками владельца):

1. Положить содержимое `.restic-password` и `.s3-env` в password manager
   (Bitwarden / 1Password — любой, синхронизируемый вне ноутбука).
2. Не хранить их копию на `E:` — тот же ноутбук, та же потеря.
3. Проверить один раз: восстановить пароль из менеджера и выполнить
   `restic snapshots` с ним.

Пока пункт не сделан, DR-план покрывает сценарии A, B, E и **не покрывает** C и D.

## Проверка плана

| Что | Как | Когда |
|---|---|---|
| снапшот `state.db` читается | `python tools/state_db_backup/verify.py` | каждые 24 ч (задача `Theseus Restore Drill`) |
| бэкап прошёл во все репозитории | лог `backup-lattice.log`: три `BACKUP_RUN status=ok` + `BACKUP_DRILL status=ok` | ежедневно 03:00 |
| репозиторий не повреждён | `restic check --read-data-subset=1%` | раз в месяц |
| восстановление реально работает | `restic restore latest` в отдельный каталог + сверка `sha256` | раз в месяц |

Проверка «файл существует» не считается: `restic check` проверяет структуру и часть
данных, `restore` — что из них реально собирается файл.

## Границы

- Локальные снапшоты `E:` **не** защищают от потери диска `E:`.
- `restic local` **не** защищает от потери ноутбука.
- GitHub хранит код, но не хранит состояние Hermes, сессии и Hindsight.
- Секреты (`API`-ключи, токены) в бэкап **не** входят: их восстановление —
  отдельная задача с отдельными ключами.
